## 1. Executive Summary

**Date:** February 7, 2026
**Version:** 3.0 (Honest Assessment)
**Status:** DEVELOPMENT — NOT PRODUCTION READY

RIINA is a formally verified programming language with Bahasa Melayu syntax, targeting security-critical applications. The project has produced a substantial body of Coq proofs (7,929 Qed in active build) covering type safety, information flow, and domain security models, along with a working prototype compiler in Rust (856 tests passing, 15 crates).

**What RIINA has today:**
- A real, compiled Coq proof base with 0 Admitted proofs and 1 justified policy axiom
- A working compiler prototype that lexes, parses, typechecks, and emits C code
- Formal proofs of type safety (progress + preservation), effect tracking, and noninterference
- Domain-specific Coq specifications covering 195 security domains (specifications, not compiler enforcement)

**What RIINA does NOT have today:**
- A production-ready compiler (prototype stage)
- Real multi-prover verification (Lean/Isabelle files are transpiled, never compiled by their respective toolchains)
- Linear types, constant-time enforcement, or secure deallocation
- Certified compliance with any standard (EAL7, DO-178C, ISO 26262 proofs are Coq specifications, not certification artifacts)
- A user community, production deployments, or third-party adoption

**Honest competitive position:** RIINA is an ambitious research project with genuine formal verification work. It is not yet competitive with production systems like CompCert, CakeML, seL4, or SPARK. The path from specification to certified product is long and resource-intensive.

## 4. Competitor Landscape (Factually Accurate)

All claims below are sourced or qualified with their timeframe. RIINA's comparison to these systems must be honest: these are mature, well-funded projects with years of engineering behind them.

### 4.1 CompCert (INRIA, as of 2025)

| Attribute | CompCert | RIINA |
|-----------|----------|-------|
| **What it is** | Formally verified C compiler (Coq) | Formally specified programming language (Coq + Rust prototype) |
| **Compiler passes** | 16 passes with 10 intermediate languages | 1 pass (direct C emission) |
| **Proof base** | ~100,000 lines of Coq, end-to-end compiler correctness | ~7,929 Qed, type safety + NI (no compiler correctness proof) |
| **Security properties** | Constant-time preservation verified since 2019 (Barthe et al., "Formally Verified Compilation of Coq-Verified Crypto") | Effect tracking, noninterference. No constant-time enforcement. |
| **Maturity** | Production-used (Airbus, nuclear), commercially licensed | Research prototype, no production users |
| **Target architectures** | x86-32, x86-64, ARM, AArch64, PowerPC, RISC-V | C emission only (via host CC) |

**Honest assessment:** CompCert is a decade+ ahead in compiler verification. RIINA's advantage is in the language design (security types, effects, noninterference) rather than compiler correctness. These are complementary, not competing, approaches.

### 4.2 CakeML (as of 2025)

| Attribute | CakeML | RIINA |
|-----------|--------|-------|
| **What it is** | Formally verified ML compiler (HOL4) | Formally specified language (Coq + Rust prototype) |
| **Compiler correctness** | End-to-end: source → machine code, verified in HOL4 | No compiler correctness proof |
| **Target architectures** | 5 architectures: x86-64, ARMv6, ARMv8, MIPS-64, RISC-V | C emission to host compiler |
| **Proof base** | ~500,000+ lines of HOL4 proofs | ~7,929 Coq Qed |
| **Security properties** | Compiler correctness preserves source semantics | Noninterference, type safety, effect tracking |
| **Maturity** | Research system with working verified binaries | Research prototype |

**Honest assessment:** CakeML has a complete verified compilation pipeline to 5 architectures. RIINA has richer security-specific properties but no verified compilation chain. CakeML's approach could inform RIINA's Phase 8 (self-hosting / translation validation).

### 4.3 seL4 (UNSW/Data61, as of 2025)

| Attribute | seL4 | RIINA |
|-----------|------|-------|
| **What it is** | Formally verified microkernel (Isabelle/HOL + C) | Formally specified programming language |
| **Scope** | Complete OS kernel with functional correctness, integrity, confidentiality | Type safety + NI for a programming language |
| **Timing channels** | Time protection under active formal verification (EvIT funded, 2023+) | No timing model or enforcement |
| **Proof base** | ~480,000 lines of Isabelle/HOL | ~7,929 Coq Qed |
| **Certifications** | CC EAL7 evaluation pathway (DARPA HACMS); used in military systems | No certifications pursued |
| **Maturity** | Deployed in military/defense/automotive | Research prototype |

**Honest assessment:** seL4 is the gold standard for verified systems software. RIINA operates at a different layer (programming language vs OS kernel). seL4's verified microkernel is referenced in RIINA's Phase 8 vision (12.3, Verified OS) but RIINA has no comparable system today.

### 4.4 Rust / RustBelt (as of 2025)

| Attribute | Rust + RustBelt | RIINA |
|-----------|----------------|-------|
| **Type system soundness** | RustBelt (POPL 2018) proved core Rust type soundness in Coq/Iris — lifetime safety, borrowing rules, Send/Sync. The rustc compiler implementation itself is unverified. | Type safety proved in Coq (progress + preservation). Prototype compiler in Rust, unverified. |
| **Memory safety** | Enforced by borrow checker at compile time. `unsafe` blocks opt out. | Modeled in Coq. Rust prototype does not enforce ownership/borrowing. |
| **Community** | Millions of users, thousands of production deployments | 0 external users |
| **Ecosystem** | crates.io (~150K+ crates) | 15 internal crates |
| **Security properties** | No built-in information flow control or effect system | Noninterference, effect tracking, security labels |

**Honest assessment:** Rust has the community, ecosystem, and tooling that RIINA lacks. RustBelt's Coq/Iris proofs are methodologically similar to RIINA's core proofs. RIINA's differentiator is the security-focused type system (information flow, effects, declassification) which Rust does not have. However, Rust's practical safety guarantees (borrow checker, no GC) are battle-tested; RIINA's are research-stage.

### 4.5 Ada / SPARK (as of 2025)

| Attribute | SPARK | RIINA |
|-----------|-------|-------|
| **Verification approach** | Contract-based: pre/postconditions proved by GNATprove (SMT-backed) | Type-system-based: properties encoded in types, proved in Coq |

**Honest assessment:** SPARK has real-world certification history that RIINA cannot match. SPARK's automated verification scales better for industrial use. RIINA's manual Coq proofs are deeper but impractical for large codebases without automation. SPARK's EAL7 is achieved certification, not a Coq model.

### 5.4 Critical Path to Competitive Position

To move RIINA from "ambitious research project" to "credible alternative," the following gaps must be closed, roughly in priority order:

1. **Compile Lean/Isabelle proofs with their native toolchains.** Until this happens, the "10-prover" claim is misleading. Only Coq proofs are compiled. Priority: HIGH.

2. **Implement constant-time enforcement.** `TConstantTime` exists as a type constructor in Coq `Syntax.v` but has no timing model, no compiler support, no enforcement mechanism. This is essential for crypto use cases. Priority: HIGH.

3. **Implement linear types.** Not in the current type system (`Syntax.v` has no linear type constructors). Required for secure deallocation, zeroization, and session types. Priority: MEDIUM-HIGH.

4. **Begin compiler correctness proof.** The gap between RIINA and CompCert/CakeML is the absence of any verified compilation. Track R (Translation Validation) provides the research foundation. Priority: MEDIUM.

5. **Pursue real certification.** The Coq compliance specs (EAL7, DO-178C, ISO 26262) are formal models of requirements, not certification evidence. Real certification requires engaging with evaluation bodies (NIAP, DERs, TUV). Priority: MEDIUM (requires funding).

6. **Build a real user community.** 0 external users. The Materialization Plan's Phase 8 community strategy (12.8) has not begun. Priority: MEDIUM.

7. **Implement cryptographic primitives.** X25519, Ed25519, ML-KEM, ML-DSA are interface-only in `05_TOOLING/crates/riina-core/src/crypto/`. No working implementations. Priority: MEDIUM.

## 6. What RIINA Actually Has That Others Do Not

Despite the honest assessment above, RIINA has genuine differentiators:

1. **Security-typed language with formal noninterference.** 201 Qed proofs across 7,852 lines of Coq. Most programming languages have NO formal information flow guarantees. Jif/Sif and FlowCaml are the closest comparisons, but both are research-only and lack RIINA's breadth of domain models.

2. **Effect system with formal algebra.** The effect gate mechanism (`kesan`/effect annotations) is formally specified and implemented. Effects are tracked at the type level with a proven lattice structure.

3. **Bahasa Melayu native syntax.** RIINA is (to our knowledge) the first formally verified language with non-English keyword syntax. This has cultural and accessibility significance for the Malay-speaking world.

4. **Broad domain coverage in formal specs.** 195 Coq domain files covering security topics from XSS to container isolation to post-quantum crypto. While these are specifications (not compiler enforcement), the breadth of formal modeling is unusual.

5. **Zero Admitted proofs in active build.** This is a genuine achievement. Many Coq projects carry Admitted proofs indefinitely. RIINA eliminated all of them (Sessions 66-76).

6. **Declassification with formal justification.** The single remaining axiom is a deliberate design choice, not a proof gap. It correctly models that declassification requires programmer justification — a sound approach to the tension between security and usability.
