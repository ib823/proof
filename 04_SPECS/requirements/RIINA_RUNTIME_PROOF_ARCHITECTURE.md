## THE INSIGHT THAT CHANGES EVERYTHING

Every verified system in history — CompCert, CakeML, seL4, HACL*, RustBelt — stops at compile time. They prove the *compiler* is correct, the *type system* is sound, the *algorithm* matches its specification. Then they hand you a binary and say: *trust us*.

**The binary runs on real hardware. Real hardware lies.**

Spectre proved CPU branch prediction leaks secrets. Rowhammer proved DRAM flips bits. Meltdown proved kernel isolation was an illusion. Intel ME proved there's a hidden computer inside your computer. Cold boot proved RAM survives power-off.

**No compiler proof survives contact with reality.**

RIINA's 13-dimension compiler verification is the strongest in history. But RIINA's doctrine is "Tak Ada Bukti, Tak Jadi Kesan" — No Proof, No Effect. That doctrine doesn't stop at the compiler. It extends to every clock cycle.

**Dimension 14: The program proves its own execution is correct. At runtime. Continuously. Cryptographically.**

This is not monitoring. This is not logging. This is not observability. This is **mathematical proof that what happened is what should have happened**, generated by the program itself as it runs.

## THE GAP: WHAT EXISTS TODAY (AND WHY IT'S NOT ENOUGH)

### What The Industry Has

| Technology | What It Proves | What It Doesn't | Who Uses It |
|---|---|---|---|
| **zkVM** (SP1, RISC Zero, Jolt) | Execution trace matches RISC-V semantics | Security properties, information flow, constant-time | Blockchain L2 rollups |
| **eBPF** | Kernel programs terminate, stay in bounds | Semantic correctness, security intent | Cilium, Falco, Tetragon (Netflix, Meta, Google) |
| **CHERI** | Memory accesses respect capability bounds | Algorithmic correctness, data flow | ARM Morello (research), CHERIoT (Microsoft embedded) |
| **Intel TDX / AMD SEV-SNP** | Memory encrypted, VM isolated from hypervisor | What code actually does inside the TEE | Google Cloud, Azure, AWS |
| **IMA (Linux)** | Binary hash matches expected value at load time | Runtime behavior after loading | Enterprise Linux |
| **Runtime monitoring** (Falco, Tracee) | System calls match expected patterns | Semantic security properties, provable guarantees | Kubernetes clusters globally |

### The Gaps Nobody Has Filled

1. **zkVMs prove execution but not security properties.** SP1 proves "these RISC-V instructions ran correctly." It says nothing about whether information flowed from Secret to Public. Nothing about constant-time. Nothing about zeroization. It's a verified calculator, not a security proof.

2. **CHERI enforces memory safety but not information flow.** Capabilities prevent buffer overflows at hardware speed. But a CHERI capability can still copy a secret key to a public buffer if the program logic says to. Memory safety ≠ security.

3. **TEEs protect from external attackers but not from the code itself.** Intel TDX encrypts memory from the hypervisor. But if the code inside the TEE has a logic bug that leaks secrets, TDX protects the leak.

4. **eBPF monitors behavior but doesn't prove correctness.** Tetragon can detect "process opened /etc/shadow." It cannot prove "this program never leaked secret data through any channel."

5. **IMA checks integrity at load time but not at run time.** IMA says "the binary that loaded is the binary you expected." It says nothing about what that binary does once running.

**Nobody has a system where runtime execution generates cryptographic proof of security property preservation.**

## RIINA'S FIVE REVOLUTIONARY RUNTIME MECHANISMS

### MECHANISM 1: PROOF-CARRYING EXECUTION (PCE)

**Concept:** Every RIINA function execution produces a cryptographic witness that the function's security contract was honored.

**How it works:**

```
┌─────────────────────────────────────────────────────────────────┐
│                    RIINA FUNCTION EXECUTION                      │
│                                                                  │
│  fn transfer_dana(                                               │
│      from: Akaun @Secret,                                        │
│      to: Akaun @Public,                                          │
│      amount: Wang @Secret                                        │
│  ) -> Keputusan @Public                                          │
│      kesan { DanaIO, Log }                                       │
│      bukti { NonInterference, ConstantTime }                     │
│                                                                  │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐           │
│  │  EXECUTE      │─>│  WITNESS     │─>│  COMPRESS    │           │
│  │  Function     │  │  Generator   │  │  via IVC     │           │
│  │  body         │  │  (inline)    │  │  (Nova)      │           │
│  └──────────────┘  └──────────────┘  └──────────────┘           │
│         │                  │                  │                   │
│         v                  v                  v                   │
│   [Actual result]   [Security witness]  [Compact proof]          │
│                                                                  │
│  Result = Keputusan {                                            │
│      value: ...,                                                 │
│      bukti: Proof {                                              │
│          non_interference: ✓ (witness: W₁),                     │
│          constant_time: ✓ (witness: W₂),                        │
│          zeroized: ✓ (witness: W₃),                             │
│          effect_gate_authorized: ✓ (witness: W₄)                │
│      }                                                           │
│  }                                                               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**What makes this different from zkVM:**

A zkVM (SP1, RISC Zero) proves: "These RISC-V instructions were executed correctly."
RIINA PCE proves: "These security properties were maintained during execution."

The difference is semantic vs. mechanical. zkVMs operate at the instruction level — they prove the CPU did what the CPU was told. RIINA PCE operates at the security level — it proves the program maintained non-interference, constant-time behavior, proper zeroization, and authorized effects.

**Technical foundation:**

- **Incrementally Verifiable Computation (IVC):** Microsoft's Nova folding scheme (CRYPTO 2024) enables updating a proof incrementally without re-proving from scratch. Each function call adds to the running proof. The proof size stays constant regardless of execution length.
- **Security-property circuits:** The RIINA compiler emits not just executable code, but also a circuit for each security property the function must maintain. These circuits are co-generated with the function body — same compiler, same type information, same verified semantics.
- **Witness generation as inline instrumentation:** The compiler inserts witness-generation code alongside execution code, similar to how profilers insert instrumentation. Overhead is real but bounded — the circuit checks security predicates, not re-executes the program.

**Precedent:** HACL*/EverCrypt proved crypto implementations correct. SNARKs for C (CRYPTO 2013) proved general C program executions. SP1/RISC Zero prove RISC-V execution at 500K-1.5M cycles/second (October 2025). RIINA's innovation: prove *security properties* specifically, not general execution, which enables dramatically smaller circuits and faster proving.

**Estimated overhead:** 
- Non-interference check: ~10-50x over native execution (comparable to ASAN overhead)
- Constant-time witness: ~5-20x (checking branch/memory patterns is simpler)
- Zeroization witness: ~2-5x (verifying specific memory locations were cleared)
- Combined with hardware acceleration (GPU proving): achievable for security-critical paths

**Key insight:** You don't prove everything. RIINA's type system already guarantees most properties at compile time. PCE only proves the residual — the properties that depend on runtime values the compiler couldn't determine statically. This makes the circuits dramatically smaller than general-purpose zkVM.

### MECHANISM 2: HARDWARE-ROOTED EFFECT ATTESTATION (HREA)

**Concept:** Every Effect Gate authorization is co-signed by hardware. Not software. Not the OS. The silicon itself.

**Architecture: Triple-Layer Enforcement**

```
┌─────────────────────────────────────────────────────────────────┐
│  LAYER 3: RIINA TYPE SYSTEM (Compile-Time)                      │
│  ─────────────────────────────────────────                       │
│  Effect types verified at compile time.                          │
│  "This function is ALLOWED to perform FileIO."                   │
│  Coq-proven sound. Lean cross-verified.                          │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  LAYER 2: eBPF KERNEL ENFORCEMENT (Runtime — OS Level)          │
│  ─────────────────────────────────────────────────               │
│  eBPF programs attached to LSM hooks verify that:                │
│  - The calling process has a valid RIINA binary hash (IMA)       │
│  - The requested effect matches the embedded effect manifest     │
│  - The capability token has not been revoked                     │
│  - The call context matches the declared session type state      │
│                                                                  │
│  Enforcement: SYNCHRONOUS. Blocks in kernel before syscall.      │
│  Overhead: ~1-5 microseconds per gate check (eBPF benchmark)     │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  LAYER 1: HARDWARE ATTESTATION (Runtime — Silicon Level)        │
│  ─────────────────────────────────────────────────               │
│  Intel TDX / ARM CCA / AMD SEV-SNP provides:                    │
│  - Memory encryption (secrets cannot be read from outside)       │
│  - Runtime Measurement Registers (RTMR) extended on each        │
│    Effect Gate invocation                                        │
│  - Remote attestation quote proving execution environment        │
│                                                                  │
│  CHERI capabilities (where available) provide:                   │
│  - Hardware-unforgeable capability tokens                        │
│  - Per-pointer bounds and permissions                            │
│  - Compartment isolation at function-call speed                  │
│                                                                  │
│  TPM 2.0 provides:                                               │
│  - Sealed storage (secrets bound to platform state)              │
│  - Platform Configuration Registers for boot chain               │
│  - Monotonic counters (anti-replay)                              │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**Why triple-layer:**

- **Layer 3 alone (compile-time):** Proves the CODE is correct. Doesn't prove the BINARY wasn't tampered with, the OS isn't compromised, or the hardware isn't lying.
- **Layer 2 alone (eBPF):** The eBPF verifier itself has had bugs (CVE-2021-3490, CVE-2022-23222, CVE-2023-2163). And eBPF runs in the kernel — a compromised kernel defeats it.
- **Layer 1 alone (hardware):** Intel TDX protects the VM but doesn't know what the code SHOULD do. CHERI prevents memory corruption but not logic bugs.

**Together:** Even if one layer is fully compromised, the other two maintain guarantees. Compile-time proofs + kernel enforcement + hardware attestation = defense in depth that has never been achieved.

**Concrete implementation:**

Every RIINA Effect Gate invocation:
1. Type system verified the call is authorized (compile-time)
2. eBPF program intercepts the syscall, validates the capability token against the binary's embedded manifest
3. On success, extends the TDX Runtime Measurement Register with a hash of (function_id | effect_type | capability_token | timestamp)
4. RTMR value can be remotely attested by anyone at any time
5. If any layer denies: **NO EFFECT OCCURS**. This is "Tak Ada Bukti, Tak Jadi Kesan" in silicon.

**Precedent:**
- Google Cloud ships Confidential VMs with Intel TDX and runtime measurement via IMA (production, 2025)
- Cilium Tetragon enforces eBPF-based kernel security policies in production at thousands of companies (2025)
- ARM Morello demonstrated CHERI hardware capabilities at ~0-65% overhead (IEEE 2024 evaluation, 20 applications including SPEC CPU2017)
- Intel TDX RTMRs enable runtime measurement extending beyond boot-time attestation (Intel documentation, 2025)

**RIINA's innovation:** Nobody has unified all three into a single coherent enforcement architecture where the compiler generates the policies, eBPF enforces them, and hardware attests to them.

### MECHANISM 3: CONTINUOUS INTEGRITY CHAIN (CIC)

**Concept:** Every state transition in a RIINA program is chained cryptographically, forming an unforgeable ledger of program behavior.

```
State₀ ──[Effect₁]──> State₁ ──[Effect₂]──> State₂ ──[Effect₃]──> State₃
  │                     │                     │                     │
  H₀                    H₁                    H₂                    H₃
  │                     │                     │                     │
  └──hash(S₀)──────────┴──hash(H₀|S₁)───────┴──hash(H₁|S₂)───────┘
                                                                    │
                                                              RTMR extend
                                                              (hardware)
```

**What this achieves:**

1. **Tamper evidence:** If any state was modified between effects, the hash chain breaks. Detectable by anyone with the chain.
2. **Non-repudiation:** The program cannot deny performing an effect. The chain is hardware-attested.
3. **Auditability:** A third party can verify the entire execution history without re-executing the program. They verify the hash chain and the PCE proofs.
4. **Temporal ordering:** Effects are totally ordered by the chain. No reordering attacks possible.

**For TELUS (anti-corruption procurement):**

This is transformative. Every procurement decision — every bid evaluation, every approval, every fund transfer — is chained. The chain is hardware-attested. A corrupt official cannot:
- Modify a past bid evaluation (chain breaks)
- Deny approving a contract (chain records it)
- Reorder events to hide timing (chain enforces order)
- Claim the system was compromised (hardware attestation proves integrity)

**The chain isn't a blockchain.** It's lighter. There's no consensus mechanism, no mining, no distributed ledger. It's a Merkle chain anchored in hardware measurement registers, extended incrementally. Think of it as a TPM PCR extend applied to application state rather than boot state.

**Performance:** SHA-384 hash per state transition ≈ 50 nanoseconds on modern hardware. Even at 10 million state transitions per second, overhead is ~0.5 seconds. Negligible.

**Precedent:**
- TPM Platform Configuration Registers use exactly this extend-hash pattern for boot measurement (TCG standard, deployed on billions of devices)
- Intel TDX RTMRs support runtime measurement extension (production 2024-2025)
- Linux IMA uses hash chains for runtime binary integrity (mainline kernel since 2005)
- Certificate Transparency logs use Merkle trees for unforgeable audit (Google, production since 2013)

**RIINA's innovation:** Apply the measurement chain at application semantic level (effects, state transitions, security decisions) rather than infrastructure level (boot, binary loading, network).

### MECHANISM 4: CONSTANT-TIME RUNTIME ORACLE (CTRO)

**Concept:** A hardware-assisted mechanism that proves operations on secrets took constant time, even against microarchitectural side channels.

**The problem no compiler can solve:**

RIINA's compiler generates constant-time code. CompCert proved it preserves semantic correctness. But:

- **The CPU lies about time.** Branch prediction, speculative execution, cache timing, port contention, frequency scaling — all cause timing variations invisible to the compiler.
- **LLVM/GCC backend can break constant-time.** Even if the RIINA frontend generates CT code, the backend optimizer may reintroduce branches. FaCT and Jasmin have documented this.
- **Hardware side channels are architectural.** Spectre v1/v2/v4/v5, RIDL, Fallout, ZombieLoad — the CPU actively leaks through timing.

**RIINA's approach: Measure, Don't Trust.**

```
┌─────────────────────────────────────────────────────────────────┐
│  CONSTANT-TIME RUNTIME ORACLE                                    │
│                                                                  │
│  STEP 1: RDTSCP Fence                                            │
│  ├── Serialize pipeline (LFENCE)                                 │
│  ├── Read Time Stamp Counter                                     │
│  └── Store as T_start                                            │
│                                                                  │
│  STEP 2: Execute security-critical section                       │
│  ├── All operations marked @ConstantTime by type system          │
│  ├── No branches on secret data (compiler-enforced)              │
│  └── No secret-dependent memory access (compiler-enforced)       │
│                                                                  │
│  STEP 3: RDTSCP Fence                                            │
│  ├── Serialize pipeline (LFENCE)                                 │
│  ├── Read Time Stamp Counter                                     │
│  └── Store as T_end                                              │
│                                                                  │
│  STEP 4: Statistical Verification                                │
│  ├── Record (T_end - T_start) for this invocation               │
│  ├── Compare against running distribution                        │
│  ├── Welch's t-test (same method as dudect tool)                 │
│  └── If timing variation exceeds threshold:                      │
│      ├── ALERT: Side channel detected                            │
│      ├── HALT: Stop processing secrets on this hardware          │
│      └── ATTEST: Record hardware anomaly in RTMR                │
│                                                                  │
│  STEP 5: Proof Generation                                        │
│  ├── After N invocations: generate statistical proof             │
│  ├── "With 99.99% confidence, execution time is independent      │
│  │    of secret values"                                          │
│  └── Proof is verifiable by third party                          │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**Why this is revolutionary:**

HACL*/EverCrypt generates constant-time code (verified in F*). But they *assume* the hardware honors constant-time semantics. RIINA *measures* whether the hardware actually does, and *proves* it statistically.

**The dudect methodology (Reparaz et al., 2017)** is the gold standard for constant-time verification: run the function on secret-dependent and secret-independent inputs, apply Welch's t-test, detect timing leakage. RIINA automates this as a runtime mechanism built into every @ConstantTime function.

**If timing variation is detected:** RIINA doesn't just log it — it halts secret processing. A compromised CPU (Spectre-class) causes a fail-secure shutdown of the security-critical path. This is "fail secure" (Law 6) applied to hardware side channels.

**Overhead:** 
- RDTSCP + LFENCE: ~30 cycles per measurement (~10ns)
- Statistical accumulation: O(1) per invocation
- t-test evaluation: every K invocations (configurable)
- Total: <100ns per @ConstantTime invocation — negligible for cryptographic operations that take microseconds

### MECHANISM 5: SELF-PROVING ZEROIZATION (SPZ)

**Concept:** When secret data is destroyed, the destruction generates a cryptographic proof that the specific memory locations were overwritten, and the proof is hardware-attested.

**The problem:**

C/C++ `memset` gets optimized away by compilers (a famous, repeated bug). `SecureZeroMemory` (Windows) and `explicit_bzero` (POSIX) exist but aren't verified. Volatile writes survive optimization but aren't proven. No system proves zeroization happened.

**RIINA's approach:**

```
ketika jatuh (kemusnahan pada nilai @Secret) {

    // 1. Record pre-zeroization hash
    biar hash_before = hash_volatile(&self, size);
    
    // 2. Perform zeroization (volatile + compiler barrier + memory fence)
    zeroize_volatile(&self, size);
    
    // 3. Read back and hash (prevents write elision)
    biar hash_after = hash_volatile(&self, size);
    
    // 4. Assert: hash_after == hash(zero_pattern)
    // 5. Extend RTMR with (allocation_id | hash_before | hash_after | timestamp)
    // 6. Generate witness for proof chain
    
    // If read-back doesn't match zero pattern:
    // PANIC — hardware is compromised or compiler broke volatile semantics
}
```

**Why this matters:**

1. **Compiler cannot optimize this away.** Volatile reads after volatile writes create a data dependency. The read-back verification creates an observable side effect.
2. **Hardware attestation makes it unforgeable.** The RTMR extension proves zeroization happened at a specific time on specific hardware.
3. **Third-party verifiable.** An auditor can request the attestation quote and verify every secret allocation was zeroized.
4. **Detects hardware failures.** If RAM has a stuck bit that prevents zeroization, the read-back catches it.

**Precedent:**
- Linux kernel's `kzfree()` and Rust's `zeroize` crate perform secure clearing but don't prove it
- NIST SP 800-88 requires media sanitization verification for classified data — RIINA automates this at the variable level
- No existing language provides provable zeroization with hardware attestation
