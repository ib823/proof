# Proof Guide — reading, building, and extending RIINA's Coq lane

This guide is for contributors who want to read, run, or extend RIINA's
machine-checked proofs. It is honest about the one thing that matters most here:
**Coq (Rocq 9.2) is the only mechanized lane.** The Lean/Isabelle/F\*/TLA+/Alloy/
SMT trees are machine-generated and are *not* independent verification — see
`website/public/metrics.json` for the per-lane claim levels. Everything below is
about the Coq corpus, which is real.

> Counts in this guide are not hardcoded — read them from the single source of
> truth, `website/public/metrics.json` (regenerated by
> `scripts/generate-metrics.sh`), or re-derive them with the commands shown.

---

## 1. Build it yourself (the only proof of a proof)

You need **Rocq 9.2** (the files use `From Stdlib`, so Coq 8.x will not work):

```bash
eval $(opam env --switch=rocq)        # put `rocq` on PATH
cd 02_FORMAL/coq
make                                  # build the whole active corpus
```

Or, from the repo root, `make coq` (delegates here) — and `make verify-all`
runs the canonical gate end to end (`riinac verify --full` recompiles the corpus
and re-derives the Qed count, then the doc-parity audit).

Build a single file (fast iteration):

```bash
cd 02_FORMAL/coq
rocq compile -Q . RIINA effects/FileIOEffectModel.v
```

The `-Q . RIINA` maps the directory to the logical prefix `RIINA`, which is why
imports read `Require Import RIINA.foundations.Syntax.`

## 2. Layout — where things are

The authoritative list of *active* files is `02_FORMAL/coq/_CoqProject` (a file
is in the build iff it is listed there; the section comments are the map):

| Directory | What it holds |
|---|---|
| `foundations/` | The core model: `Syntax.v` (types, expressions, effects, taint, capabilities), `Semantics.v`, `Typing.v`, and the numeric-tower models (`SizedInt.v`, `BigIntModel.v`, `DecimalModel.v`, `FixedPointModel.v`) |
| `type_system/` | `Progress.v`, `Preservation.v`, `TypeSafety.v` — the syntactic type-safety results |
| `effects/` | `EffectAlgebra.v` (the join-semilattice), `EffectSystem.v` (`effect_safety`), `EffectGate.v`, `FileIOEffectModel.v` |
| `properties/` | Supporting lemmas — inversion, canonical forms, store safety, declassification, non-interference development |
| `termination/` | Sized types, reducibility, strong normalization |
| `domains/` | The large domain corpus — `VerifiedFileSystem.v`, `TaintSystemCorrectness.v`, crypto, blockchain, Syariah, OS/kernel, choreography, CRDTs |

Files under `_archive_deprecated/` or commented out in `_CoqProject` are **not**
in the active build (often because they contained unprovable admits); do not cite
their contents as verified.

## 3. The rules that are not negotiable

These are enforced by the pre-commit/pre-push hooks and by `riinac verify`:

1. **Zero `Admitted`** in the active build. A proof is `Qed.` or it is not in the
   corpus. (`CLAUDE.md` forbids committing `Admitted`.)
2. **Zero `Axiom`** in the active build.
3. **`Parameter` declarations are the Trusted Computing Base.** A small number of
   `Parameter`s model the trusted hardware/primitive interface; they are
   logically axioms and are tracked explicitly in the proof ledger `AXIOMS.md`
   (repo root, regenerated by `scripts/update-proof-ledger.sh`).
   If you add one, you are widening the TCB — justify it in the ledger.
4. **Counts are re-derived, never copied.** The published Qed/axiom counts come
   from commands (`scripts/generate-metrics.sh`), and `scripts/audit-docs.sh`
   fails the commit if any doc disagrees with `metrics.json`.

Verify the integrity invariants yourself (the `grep -E '\.v$'` keeps only the
file lines from `_CoqProject`, dropping its `-Q`/`-arg` options):

```bash
cd 02_FORMAL/coq
grep -rlE "^[[:space:]]*Admitted\." $(grep -E '\.v$' _CoqProject)   # must print nothing
grep -rlE "^[[:space:]]*Axiom "     $(grep -E '\.v$' _CoqProject)   # must print nothing
```

## 4. Adding a proof file

1. Create `02_FORMAL/coq/<area>/MyModule.v`. Start from the standard header:

   ```coq
   (* Copyright (c) 2026 The RIINA Authors. All rights reserved. *)
   Require Import RIINA.foundations.Syntax.
   (* ... only the imports you need ... *)
   ```

2. **Register it** by adding the path to `_CoqProject` under the right section
   comment. A file not in `_CoqProject` is invisible to `make` and to the Qed
   count — this is the single most common mistake.

3. Build it: `rocq compile -Q . RIINA <area>/MyModule.v`. Iterate until `Qed.`

4. Build the whole corpus (`make`) to catch ordering/dependency breakage, then
   run `scripts/update-proof-ledger.sh` and `scripts/generate-metrics.sh` so the
   ledger and metrics pick up your new Qeds, and `scripts/audit-docs.sh` to
   confirm parity.

## 5. The pattern that makes proofs bite: Coq ⇄ Rust parity

A proof about a *model* is only worth what its connection to the *shipped code*
is. RIINA's idiom for that connection — used by `BigIntModel.v`,
`DecimalModel.v`, `FixedPointModel.v`, and `FileIOEffectModel.v` — is an
**executable KAT cross-check**:

1. In the `.v` file, state the algebraic property and prove it (`Qed`), then pin
   concrete inputs with `vm_compute` examples:

   ```coq
   Example kat_file_read :
     (file_op_effect FOpRead, file_op_arg FOpRead, file_op_ret FOpRead)
     = (EffFileSystem, ShString, ShTaintedString).
   Proof. vm_compute. reflexivity. Qed.
   ```

2. In Rust, write a test that asserts the *running code* reproduces exactly those
   pinned values, naming the Coq file:

   ```rust
   // mirrors 02_FORMAL/coq/effects/FileIOEffectModel.v (kat_file_* rows)
   #[test]
   fn file_builtin_table_matches_coq_model() { /* assert the checker's table */ }
   ```

Now a divergence on *either* side fails the Rust test. The Coq proof gives you
the theorem; the parity test gives you the guarantee that the binary you ship
behaves like the thing you proved. When you model a piece of the implementation,
add the matching parity test — that is the house style.

A worked example of building one of these from scratch is the File-I/O effect
model: `02_FORMAL/coq/effects/FileIOEffectModel.v` (19 Qed) ⇄
`file_builtin_table_matches_coq_model` in
`03_PROTO/crates/riina-typechecker/src/tests.rs`.

## 6. Extending the type/effect system (end-to-end)

Adding a feature usually means touching both the proof and the checker, in this
order:

1. **Model** it in `foundations/Syntax.v` (+ a typing rule in `Typing.v` or an
   effect in `effects/EffectAlgebra.v`) and prove the property you care about.
2. **Enforce** it in `03_PROTO/crates/riina-typechecker/src/lib.rs`, mirroring
   the Coq rule; cite the theorem in a comment.
3. **Pin** the correspondence with a parity test (§5) and end-to-end `riinac
   check`/`run` tests.
4. **Record** the gap honestly: if the checker enforcement is narrower than the
   proof (the common case — see REQ-27 in `RIINA_MASTER_PLAN.md`), say so in the
   plan's Part 2/Part 11, not just in a comment.

The REQ-27 secret-sink work is a small, complete example of this loop:
`Declassification.v` (proof) → `secrecy_at_sink` (checker) → typechecker + e2e
tests (parity) → REQ-27 row (honest scope).

## 7. Verifying the whole thing

```bash
make verify-all          # build riinac, riinac verify --full (recompiles Coq,
                         # re-derives Qed, runs all Rust tests), then audit-docs
```

`riinac verify --full` is the single source of truth (the pre-push hook runs it).
A `--fast` variant (`make verify`) does a static Qed scan and the Rust tests but
skips the heavy Coq recompile — use it locally, but the full build is what counts.
